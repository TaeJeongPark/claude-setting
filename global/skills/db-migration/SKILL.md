# DB 마이그레이션 작성

## 1. 도구와 관례 파악

- 마이그레이션 도구와 위치를 찾는다: `db/migration/V*__*.sql`(Flyway), `db/changelog`(Liquibase), `alembic/versions`, `prisma/migrations`.
- 기존 파일 3~4개를 읽고 이름 규칙, 버전 번호 방식(정수/타임스탬프), 스키마 지정, 주석 스타일을 따른다.
- 다음 버전 번호는 기존 최댓값에서 정한다. 다른 브랜치와 번호가 겹칠 수 있으면 사용자에게 알린다.
- 이미 적용된 마이그레이션 파일은 절대 수정하지 않는다.

## 2. 엔티티/매퍼와 맞추기

- JPA를 쓰면 Entity 필드, 컬럼 타입, nullable, 길이가 마이그레이션과 일치하는지 확인하고 함께 수정한다(`ddl-auto=validate`가 깨지지 않게).
- MyBatis를 쓰면 영향을 받는 Mapper XML의 `resultMap`과 쿼리 컬럼 목록을 함께 수정한다.

## 3. 무중단 안전성 점검

운영 테이블을 건드리면 아래를 확인하고, 해당하면 단계를 나눈다.

| 변경 | 안전한 방법 |
|---|---|
| 인덱스 추가 | `CREATE INDEX CONCURRENTLY` (트랜잭션 밖에서 실행해야 하므로 Flyway는 해당 파일에 트랜잭션 비활성 설정) |
| NOT NULL 컬럼 추가 | nullable로 추가 → 백필 → `SET NOT NULL` (큰 테이블은 `CHECK ... NOT VALID` → `VALIDATE` 후 전환) |
| 기본값 있는 컬럼 | PG 11+는 상수 기본값이면 즉시 처리되지만, 휘발성 함수 기본값은 테이블을 다시 쓴다 |
| 컬럼 이름 변경·삭제 | 코드가 더 이상 쓰지 않게 먼저 배포 → 다음 마이그레이션에서 삭제 |
| 타입 변경 | 테이블 재작성 여부 확인. 위험하면 새 컬럼 추가 → 복사 → 전환 |
| 외래키 추가 | `NOT VALID`로 추가 → `VALIDATE CONSTRAINT` |

## 4. 작성 규칙

- 한 마이그레이션에는 하나의 논리적 변경만 담는다.
- 되돌리기 방법을 정해 둔다: 도구가 down/rollback을 지원하면 작성하고, Flyway 커뮤니티판이면 되돌리는 SQL을 PR 본문에 적는다.
- 외래키 컬럼에는 인덱스를 만든다. 타입 규칙은 `~/.claude/rules/postgresql.md`를 따른다.

## 5. 검증 (적용은 하지 않는다)

- 로컬/Testcontainers 통합 테스트가 있으면 돌려서 마이그레이션이 깨끗한 DB에 적용되는지 확인한다.
- 실제 DB(로컬 포함)에 `migrate`를 실행하기 전에는 사용자 확인을 받는다.
- 보고에 포함할 것: 파일 경로, 변경 요약, 락·다운타임 위험, 배포 순서(코드 먼저/마이그레이션 먼저), 되돌리기 방법.
