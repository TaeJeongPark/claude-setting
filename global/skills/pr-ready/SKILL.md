# PR 준비

## 1. 범위 파악

- 기본 브랜치를 확인하고(`git symbolic-ref refs/remotes/origin/HEAD`), `git fetch` 후 `git log --oneline origin/<base>..HEAD`와 `git diff origin/<base>...HEAD --stat`으로 변경 범위를 본다.
- 기본 브랜치에 있다면 작업 브랜치를 먼저 만든다.
- 커밋되지 않은 변경이 있으면 이번 PR에 포함할지 사용자에게 묻는다.

## 2. 셀프 리뷰

`git diff origin/<base>...HEAD`를 리뷰어 입장에서 읽고 다음을 찾는다:

- 디버그 코드, 주석 처리된 코드, 임시 로그, TODO, 하드코딩된 비밀값·URL
- 요청 범위를 벗어난 변경(포매팅만 바뀐 파일, 무관한 리팩터링)
- 누락된 테스트, 에러 처리, 마이그레이션·문서 갱신
- 언어별 규칙(`~/.claude/rules/`) 위반

찾은 문제는 고치고, 고칠 수 없는 것은 PR 본문의 "리뷰 포인트"에 적는다.

## 3. 검증

`verify` 스킬 절차대로 검사를 실행한다. 실패가 남아 있으면 PR을 만들지 않고 보고한다.

## 4. 커밋 정리

- 프로젝트 커밋 관례(없으면 Conventional Commits)를 따르는지 확인한다.
- 이미 push한 브랜치의 히스토리는 rewrite하지 않는다. 정리가 필요하면 사용자에게 묻는다.

## 5. PR 작성

- `.github/pull_request_template.md` 등 템플릿이 있으면 그 구조를 따른다.
- 없으면 아래 구조로 쓴다:

```markdown
## 배경
왜 이 변경이 필요한가 (이슈 링크)

## 변경 사항
- 핵심 변경을 리뷰 순서대로

## 검증
- 실행한 검사와 결과, 수동 확인 방법

## 리뷰 포인트 / 위험
- 마이그레이션, 설정 변경, 하위 호환성, 배포 순서
```

- push와 PR 생성은 사용자가 요청한 경우에만 한다. 요청이 없으면 제목과 본문 초안을 보여 주고 멈춘다.
